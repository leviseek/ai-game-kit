# Implement Config Service v1 — Design

## Context

框架已具备分层模式：`contracts/*`（纯接口与类型化错误）、`core/*`（引擎无关实现）、`adapters/memory/*` 与 `adapters/cocos/*`（注入接缝）、`tests/framework/foundation/*.test.ts`（bun）。资源层 `IResourceProvider` 已支持 `kind: "asset"` 加载与 `LoadCoordinator`/`ResourceScope` 语义；`versioned-storage` 已提供玩家存档的命名空间/版本化/迁移能力。设计决策 11 明确"静态配置与玩家存档分开管理：配置随版本发布，存档随玩家变化"。本 change 在其上实现配置服务，配置经资源读取路径而非存档键值后端。

## Goals / Non-Goals

**Goals:**
- 提供引擎无关的配置服务：类型化读取、缺失/解析失败类型化错误、默认值回退、只读快照
- Bundle 配置加载适配器：复用资源层加载能力，不与玩家存档混用
- 严格类型化，内核不依赖 `cc`，根入口白名单同步

**Non-Goals:**
- 不实现配置热更新、配置版本化迁移（配置随版本发布，重装即可，不做玩家级迁移）
- 不实现配置 Schema 校验器（类型化读取即校验，不引入 JSON schema 依赖）
- 不实现运行时配置写入或玩家可修改配置（写路径属存档，见 versioned-storage）
- 不实现加密或远程配置下发

## Decisions

### 1. 内核采用"配置表 + 只读快照"模型

配置服务装载后持有不可变配置表，读取按键返回类型化值；快照通过冻结对象（`Object.freeze` 或等价不可变封装）暴露，防止运行时修改。

- **理由**：配置只读语义直接对应 spec 快照需求；内核为纯状态管理，可脱离引擎测试。
- **备选**：每次读取做深拷贝。开销无必要，快照共享只读结构即可。

### 2. 类型校验用最小声明式检查，不引入 schema 依赖

读取时按调用方声明的类型做运行时形状检查，类型不匹配、缺失、解析失败分别产出类型化错误。

- **理由**：项目约束不主动引入新依赖；最小形状检查足以支撑类型化读取与分支处理。
- **权衡**：检查覆盖基础形状（对象/数组/标量），不构建完整 schema 验证器；更严格需求留给具体游戏层。

### 3. 配置经资源层加载，不触达存档后端

Bundle 配置加载适配器经 `IResourceProvider.load`（`kind: "asset"`）读取配置资源并解析为配置表，全程不接触 `PlatformStorage`/`VersionedStorage`。

- **理由**：设计决策 11 的分离边界由此在实现层落实；复用加载去重与作用域语义，不重建加载逻辑。
- **备选**：配置存到键值后端。会把配置生命周期与玩家存档耦合，违反设计决策 11 与 spec"互不混用"。

### 4. 无业务配置模型

服务不定义具体游戏配置结构；配置内容以 JSON/类型化资源表达，游戏层声明键与类型。

- **理由**：与既有架构一致，配置结构属 `game` 层。

## Risks / Trade-offs

- [配置解析失败静默回退] → 一律类型化报错且不产生部分状态，测试覆盖失败路径。
- [类型化读取与配置实际形状漂移] → 读取时形状检查拦截，错误携带键名诊断；配置发布流程配合更新声明类型。
- [只读快照被强转绕过] → 只读通过冻结结构保证，读取方拿到快照即不可变；框架不提供可变访问路径。
- [配置与存档意外混用] → 加载路径显式走资源层，并测试断言不触达存档后端。

## Migration Plan

无存量迁移。实现顺序为 TDD：先写 `tests/framework/foundation/config.test.ts` 覆盖 spec 场景（红期），再实现 `contracts/config/*` 与 `core/config/*` 至转绿；随后实现 Bundle 配置加载适配器集成测试；最后同步根入口白名单。归档前执行 ADR 检查。

## Open Questions

无。快照不可变性、类型校验范围与资源接入方式已在 Decisions 落定，不改变 spec 行为契约。
