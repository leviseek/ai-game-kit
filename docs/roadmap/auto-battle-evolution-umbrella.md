# 自动战斗玩法进化大提案（Umbrella Proposal）

> 定位：顶层规划文档 / 路线图（roadmap）。本文只确定方向、原则与分批边界，不进入实现。
> 适用范围：`assets/samples/game_auto_battle/`（logic / models / view / assembly）与 `ui/demo/assets/AutoBattle/`。
> 关联既有资产：`openspec/specs/auto-battle-playable/spec.md`、`doc/decisions/ADR-013/ADR-017`、framework 的 `WallClock` / `SimulationClock` / platform-storage / versioned-storage。
> 推进方式：本文的每个阶段、每个 change 落地为**独立的小 OpenSpec change**，按依赖顺序逐个 `propose → apply → archive`，遵循 `openspec/config.yaml` 的 operations（含每个 change 末尾的 ADR 检查任务）。

---

## 1. 概述

`game_auto_battle` 目前是一个确定性良好、引擎无关、事件驱动、但**纯观战**的单局 demo：玩家启动后只能看，不能操作、不能成长、不能挂机。本次大提案的目标是把该玩法从"观战型单局 demo"演进为"**可操作、可成长、可挂机**的完整玩法"。

演进遵循五个已确认的项目决策：

| 编号 | 决策 | 说明 |
|---|---|---|
| D1 | 方向确认 | 演进为可操作、可成长、可挂机的完整玩法 |
| D2 | 布局取向 | **敌方在左、己方在右**（对波左边输梗）——现状是上下对阵，需重构布局 |
| D3 | 布阵编辑 | 第一版用**点击选择**填充槽位，不上拖拽 |
| D4 | 特效投入 | 第一版接受**像素风命中反馈**（飘字 + 受击闪白/抖动），不做复杂序列帧光效 |
| D5 | 挂机收益 | 按**离线分钟**计算；本地存储（复用 ADR-017 能力）；设计预留服务器演进空间 |

9 个改进点组织为 **4 个阶段、9 个独立小 change**：

```
Stage 0（P0 观战体验）  01 左右对阵 · 02 血蓝条区分 · 03 加速挡位
Stage 1（P1 玩法核心）  04 规模可配置 · 05 布阵编辑 · 06 锁定目标
Stage 2（P2 表现增强）  07 命中反馈特效 · 08 入场/移动/瞬移
Stage 3（P3 长线系统）  09 自动挂机（离线收益）
```

---

## 2. 目标与非目标

### 2.1 目标

- 战斗**布局**符合 D2：敌方左、己方右，为后续坐标式渲染与位移表现打底。
- 观战体验可调：血蓝条视觉可区分（D 相关）、加速挡位可切换，且**不改变战斗逻辑结果**（确定性）。
- 玩法可操作：规模可配置（NvN）、布阵可编辑（点击选择，D3）、单位可锁定目标。
- 战斗表现可感知：命中反馈特效（飘字 + 闪白/抖动，D4）、单位入场/移动/瞬移。
- 玩法可挂机：离线收益按"离线分钟"结算并本地持久化（D5），为未来服务器化预留迁移点。

### 2.2 非目标（本次路线图明确不做）

- **不做战斗中的手动操作**（手动选目标、主动施法、微操走位）：战斗过程仍为自动，"可操作"本次仅覆盖编队与加速。
- **不做完整英雄成长系统**（等级、装备、突破、技能升级）：9 个改进点不含成长本体；挂机收益为成长产出资源做铺垫，成长系统属于后续独立提案。
- **不做复杂序列帧光效**（D4）：特效仅限飘字 + 闪白/抖动；不引入粒子系统、序列帧动画、外部位移骨骼。
- **不做服务器同步与账号体系**（D5）：本次挂机为本地存储；服务器迁移点只做设计预留，不实现。
- **不做拖拽布阵**（D3）：第一版仅点击选择。
- **不改变战斗结算规则本身**（伤害/治疗/能量公式、回合机制）：本提案只增加"目标锁定"选择策略，不改数值模型。

## 3. 总体设计原则

以下五条原则贯穿所有 change，是拆分与实现时必须遵守的统一基线。

### 3.1 战斗逻辑层保持引擎无关与确定性（tick 驱动、事件广播）

现状已满足，**必须保持**：

- `logic/` 不依赖 cc/fgui（现有负向边界测试锁定），继续由 **tick 单行动推进**驱动。
- 战斗变化以 **事件（`AutoBattleEvent`）** 广播 + 保序记录，事件是逻辑层对外的唯一"语义流"。
- 确定性：速度稳定排序 + 纯函数结算 + 固定行动序列。**新增逻辑（锁定目标、任意规模）必须保持同输入同结果**，可重放、可测试。

演进约束：

- 所有玩法规则（目标锁定、规模、编队实例化）在 logic 层完成；表现层只消费事件与状态快照，**不得反向影响 tick 序列**。
- 加速挡位**只改驱动节拍，不改 tick 内容**——同一对局在任何挡位下产生的事件序列必须完全一致（作为测试断言）。

### 3.2 表现层扩展建立在事件层之上（事件投影，状态为准）

- 渲染仍以 `state` 快照为**最终真相**（现状 `render()` 基于不可变快照，保留）。
- 特效/位移作为**事件消费者**（event projection）：监听 `attack` / `skill-damage` / `skill-heal` / `unit-dead` / `round-start` 驱动飘字、闪白、抖动、位移动画；动画是叠加在最终状态之上的"演示层"，逻辑层不等动画完成。
- 推荐演化：presenter 从"每 tick 全量重建 VM"演进为"**state 全量渲染 + 事件增量动画**"，动画结束后回到 state 快照对应的姿态，避免状态漂移。
- FGUI 自建组件禁止手写 transition（AGENTS 第 10 条）：飘字/闪白/抖动/位移全部由 **TS 驱动**（alpha/xy/controller selectedIndex），在 `view/` 层实现。

### 3.3 编队数据模型（lineup + 英雄池）作为共享底座

规模可配置（04）与布阵编辑（05）需要一个统一的数据模型，避免两处各造一套：

```
HeroPool（英雄池，静态配置/不可变） → Lineup（玩家编队，可变、可持久化） → 战斗实例化
```

- **HeroPool**：候选英雄清单（id、name、属性、技能），来源为配置表扩展（现状 `teams.ally/enemy` 演进为 `heroes` 池 + 初始 lineup）。
- **Lineup**：玩家当前上阵编队 = 槽位序列（slot 0..N-1 → hero id）；是可变的玩家状态，开战时由 lineup 实例化战斗单位，**战斗实例化后与 lineup 解耦**（战斗内修改不影响存档编队）。
- 规模（04）定义"槽位数量上限与显隐"；布阵（05）操作 lineup；挂机（09）可把 lineup 作为收益速率的输入（可选，第一版可固定速率）。
- 涉及持久化时复用 versioned-storage（ADR-013）做 schema 版本化。

### 3.4 空间坐标从"标签式"演进为"坐标式"

现状 `position: "front" | "mid" | "back"` 是**标签**，渲染靠 VM 固定槽位顺序硬编码（`unit_0..5`）。本路线图把空间语义分三层渐进：

| 层 | 语义 | 落点 |
|---|---|---|
| 逻辑槽位 | `side + slotIndex`（0..N-1）决定目标选择优先级、实例化顺序 | change 04 |
| 渲染映射 | slot → 屏幕坐标映射表（敌左、己右），由布局配置驱动 | change 01（映射表）、05（编队页） |
| 表现坐标 | 渲染坐标的插值/偏移（位移、闪白、飘字锚点） | change 07、08 |

- **保留** `position` 标签作为目标选择优先级语义（前排优先），**新增** slot/坐标用于布局与表现；标签与坐标由映射函数单向推导，避免双真源。
- 坐标演进是跨 change 的主线，建议在 04 落地时**先落 ADR-025**（见第 6 节），避免后续返工。

### 3.5 本地存储挂机设计预留服务器演进空间（D5）

- **本次存储边界**：挂机状态（`lastSeenAt` 墙钟时间戳 + 累计收益 + schema 版本）存本地（platform-storage + versioned-storage）；收益计算为**纯函数** `computeIdleRewards(lastSeenAt, now, rate) → { minutes, rewards }`。
- **时间源分离**：战斗用模拟钟（确定性），挂机用墙钟（真实时间，framework 已有 `WallClock`）。当前 presenter 用 `Date.now()` 驱动模拟钟 advance 的混合逻辑要在 09 中理清：**模拟钟仍由测试/驱动推进，墙钟仅服务挂机结算**。
- **服务器迁移点（明确标注，本次不实现）**：
  1. 存储端口抽象（`IdleRewardStore` 接口）：本次用本地实现，未来替换为远程实现，业务层不感知。
  2. 收益计算纯函数：未来改为服务器权威校验（防作弊），本地仅做展示性预计算。
  3. schema 版本化：versioned-storage 保证未来新增字段/迁移可演进。
  4. 时间源：未来以服务器时间为准，本地墙钟仅作参考。

## 4. 分阶段路线图

> 命名：change 目录名建议 `openspec/changes/<change-name>/`（kebab-case）。实现仍走 `propose → apply → archive`。
> 依赖方向：`→` 表示"必须在其后"；`⟂` 表示可与前序并行但建议顺序执行（减少 FGUI 重复发布）。

### Stage 0（P0 观战体验基础）

#### change-01：`battle-layout-enemy-left`（左右对阵）

- **做什么**：把 `AutoBattleView.xml` 从上下对阵（敌上、己下）重构为**敌左、己右**（D2）；同步更新 VM 槽位 → 屏幕坐标的渲染映射（引入 slot→xy 映射表雏形）；更新冒烟/截图与相关测试断言。
- **不做什么**：不改 `logic/`（side 语义、目标选择、实例化顺序均不变）；不引入完整坐标式模型（只做渲染映射层）。
- **核心交付物**：布局重构后的 FGUI 页面（委派 fgui-designer + `bun run fgui validate`）；`view/` 渲染映射表；VM/冒烟测试更新。
- **依赖**：无（全路线图最基础）。
- **建议顺序**：Stage 0 第一。它是 07/08 表现坐标的锚点。

#### change-02：`battle-status-bar-visuals`（血蓝条区分）

- **做什么**：视觉上区分 HP 条与能量条（当前共用 `CommonProgressBar` 样式无法区分）——如 HP 红色、能量蓝色/绿色、或不同高度与标签；纯表现调整，不改数据模型（`hp/energy` 字段已具备）。
- **不做什么**：不新增字段、不改 battle 逻辑；不引入新的进度条组件类型（如可复用 Common 内新增样式变体需先经 fgui-designer 评估）。
- **核心交付物**：HP/能量条可区分的 FGUI 样式；VM 绑定不变或微调（如条名对齐）；截图验证。
- **依赖**：`01 →`（同页面，先重构布局再做样式可减少重复发布；若并行则必须提交前统一 validate）。
- **建议顺序**：Stage 0 第二（紧随 01）。

#### change-03：`battle-speed-control`（加速挡位）

- **做什么**：提供 1x / 2x / 3x 挡位切换；改变 presenter 的驱动节拍（推荐 `AutoBattleClock` 增加倍率语义或 presenter 层按挡位换算 `advance` 量）；UI 增加挡位按钮与状态显示。
- **不做什么**：不改战斗逻辑与 tick 内容；不改变事件序列与终局结果。
- **核心交付物**：挡位状态 + 按钮命令绑定；节拍驱动更新；**确定性测试**（同一对局不同挡位事件序列一致）。
- **依赖**：无（driver/presenter 层独立）。
- **建议顺序**：Stage 0 第三（可与 01/02 并行，独立验证）。

**Stage 0 里程碑**：敌左我右布局正确；血条/能量条可区分；加速挡位可切换且对局结果不变。

### Stage 1（P1 玩法核心）

#### change-04：`battle-scale-config`（规模可配置）

- **做什么**：从固定 3v3 演进为 NvN（N 可配置，建议首版上限 **6**，即 1280×720 下每侧最多 6 槽）；`config` 解析支持任意数量单位并校验上限；引入**逻辑槽位模型**（`side + slotIndex`）作为实例化与目标选择的稳定身份；VM/渲染从固定 6 槽位演进为按规模预置槽位 + 显隐（FGUI 预置最大规模槽位，按 `teamSize` 显示）。
- **不做什么**：不做完整 lineup/英雄池（05 做）；不改变伤害/能量规则；不改渲染坐标体系（仅槽位数量动态化）。
- **核心交付物**：任意规模可开战的逻辑层（含 `1v1`/`5v5`/`6v6` 测试）；FGUI 槽位预置与显隐；VM 动态槽位绑定。
- **依赖**：`01 →`（布局映射表先定）；是 `05 →` 的前置。
- **建议顺序**：Stage 1 第一。**此 change 落地时建议一并落 ADR-025**（坐标式战斗单元模型）。

#### change-05：`lineup-editor-click`（布阵编辑——点击选择）

- **做什么**：实现 **HeroPool + Lineup** 数据模型（3.3）；提供编队页面：候选英雄区 + 上阵槽位区；**点击选择**（D3）：点击候选英雄填入空槽/替换选中槽，点击已上阵英雄可卸下；开战时由 lineup 实例化战斗单位。
- **不做什么**：不做拖拽（D3 排除）；不做英雄成长/解锁（非目标）；不做阵容战力预估等附加系统。
- **核心交付物**：HeroPool/Lineup 模型与持久化（versioned-storage）；编队 FGUI 页面（fgui-designer）；点击交互命令；从编队开战的装配链路（assembly 接线）；测试（点击填充/卸下/持久化恢复）。
- **依赖**：`04 →`（槽位模型）；`01 →`（编队页布局沿用敌左己右语义可选）。
- **建议顺序**：Stage 1 第二。**建议一并落 ADR-026**（编队数据模型）。

#### change-06：`target-lock`（锁定目标）

- **做什么**：目标选择从"每次行动重新选前排"改为"**单位锁定目标直至其死亡/不可攻击**"：战斗单位为 `lockedTargetId` 状态；`formation` 选择策略更新（锁定优先、目标死亡后按前排优先重选）；`state` 快照暴露锁定关系（可选）。
- **不做什么**：不改伤害/技能数值；不做仇恨/嘲讽等扩展（留待未来）。
- **核心交付物**：锁定目标状态与选择策略；事件/快照反映锁定；测试（目标死亡前不换目标、死亡后顺延）。
- **依赖**：`04 →`（规模模型统一后目标选择更易改）；无 FGUI 强依赖。
- **建议顺序**：Stage 1 第三（可与 05 并行开发，但逻辑层改动在 04 之后更稳）。

**Stage 1 里程碑**：任意规模可正常对局；点击布阵生效且可持久化；锁定目标行为正确（目标死亡前不换、死亡后顺延）。

### Stage 2（P2 表现增强）

#### change-07：`hit-feedback-effects`（命中反馈特效）

- **做什么**：像素风命中反馈（D4）：**伤害飘字**（事件 `value` 上浮淡出）+ **受击闪白/抖动**（目标节点短时变色/位移）；作为事件投影器挂在 presenter/view 层（3.2）。
- **不做什么**：不做序列帧光效、粒子、复杂动画（D4 排除）；不改逻辑层。
- **核心交付物**：飘字/闪白/抖动动画（TS 驱动，禁 transition）；事件→特效投影器；FGUI 特效节点（像素风数字/闪白遮罩，需 fgui-designer + sprite 生成）；测试（事件触发特效）。
- **依赖**：`01 →`（单位屏幕坐标锚点）；`04 →`（动态槽位下按单位 id 定位）。
- **建议顺序**：Stage 2 第一。

#### change-08：`unit-motion`（入场/移动/瞬移）

- **做什么**：单位表现位移：**入场**（战斗开始从场外/敌方侧进入站位）、**攻击位移/抖动**（攻击时向目标方向前冲或受击后撤）、**瞬移**（治疗/技能目标切换时表现跳变，如需）；基于事件（`round-start`/`attack`/`skill-heal`）+ slot→xy 映射插值。
- **不做什么**：不做格子寻路/路径动画（瞬移即可）；不改逻辑坐标（位移是表现层插值，逻辑 slot 不变）。
- **核心交付物**：入场/前冲/瞬移动画（TS 驱动）；与 07 特效统一的动画协调（同队列或互斥策略）；测试（动画终态回到 state 姿态）。
- **依赖**：`01 →`（坐标）、`07 →`（动画机制可复用）、`04 →`（槽位模型）。
- **建议顺序**：Stage 2 第二。**07/08 落地时建议落 ADR-027**（事件驱动表现层：动画不破坏确定性）。

**Stage 2 里程碑**：命中飘字/闪白/抖动正确；入场/移动/瞬移与事件对应；动画结束终态与逻辑状态一致。

---

### Stage 3（P3 长线系统）

#### change-09：`idle-rewards-offline`（自动挂机——离线收益）

- **做什么**：按 **离线分钟** 计算收益（D5）：记录 `lastSeenAt`（墙钟）；返回/定时结算 `computeIdleRewards`；本地持久化挂机状态（platform-storage + versioned-storage）；提供挂机 UI（离线时长、收益预览、领取/自动入账）。
- **不做什么**：不做服务器同步/账号（D5 非目标）；不做收益消耗系统（成长系统非目标）；收益速率第一版可固定或由 lineup 规模/星级加权（可选）。
- **核心交付物**：`IdleRewardStore` 端口（本地实现 + 未来远程替换点）；纯函数收益计算；挂机状态版本化 schema；挂机 FGUI 页面；测试（离线分钟结算、重启保留、schema 迁移）。
- **依赖**：`05 →`（lineup 可作为速率输入，可选）；framework platform-storage/versioned-storage（已有）。
- **建议顺序**：Stage 3 第一（本阶段唯一）。**建议落 ADR-028**（挂机收益本地存储边界与服务器迁移点）。

**Stage 3 里程碑**：离线 N 分钟返回收益正确；重启后收益保留；schema 可版本化迁移；服务器迁移点文档明确。

## 5. 关键架构决策点（ADR 建议清单）

openspec 约定每个 change 的 tasks.md 末尾必须有 ADR 检查任务。本提案预判以下 4 个新增 ADR 决策点（现有编号至 ADR-024，建议编号顺延）：

| 建议 ADR | 名称（slug） | 触发 change | 核心问题 | 倾向结论 |
|---|---|---|---|---|
| ADR-025 | coordinate-battle-unit-model | 04 | 空间语义如何从标签式（front/mid/back）演进为坐标式（slot）？谁是真源？ | 保留 position 标签作为目标选择语义；新增 `side+slotIndex` 逻辑槽位与 slot→xy 渲染映射表，映射单向推导，避免双真源 |
| ADR-026 | lineup-data-model | 05 | HeroPool 与 Lineup 如何建模、谁拥有可变性、何时持久化？ | HeroPool 静态配置不可变；Lineup 玩家可变、versioned-storage 持久化；开战时由 lineup 实例化战斗单位并与存档解耦 |
| ADR-027 | event-driven-presentation | 07/08 | 特效/位移如何建立在事件层上而不破坏确定性？ | 事件投影 + state 快照为准；动画可打断、终态回到快照姿态；逻辑层不等动画完成 |
| ADR-028 | idle-reward-local-storage-boundary | 09 | 本地挂机存储的边界在哪？服务器迁移点如何预留？ | 收益纯函数化 + `IdleRewardStore` 端口抽象 + schema 版本化；时间源区分（战斗模拟钟 / 挂机墙钟）；未来服务器权威校验 |

> 说明：加速挡位实现（timeScale vs 节流换算）、FGUI 槽位预置策略等属于**局部决策**，在 change 内记录决策依据即可，不必单独 ADR。

## 6. 风险与依赖

| 风险 | 影响 | 缓解 |
|---|---|---|
| FGUI 改动密集（布局/槽位/特效/编队/挂机 5 个 change） | 违反 FGUI 工作流则产生无效产物 | 每个 FGUI change 必须委派 fgui-designer、产出 XML 后 `bun run fgui validate --strict` 通过才可发布（AGENTS 既有约束） |
| 确定性被表现层破坏（加速/特效/位移） | 对局结果漂移、测试失效 | 确定性测试锁定：加速不同挡位事件序列一致；动画终态回到 state 快照；逻辑层不做表现感知 |
| 坐标演进返工 | slot 模型与旧固定槽位并存混乱 | 04 先落 ADR-025，渲染映射表在 01 就定雏形，后续 change 只演进不重构 |
| 规模上限牵动 FGUI 结构 | 槽位 XML 写死导致扩展难 | 首版定最大规模（建议 6）并预置槽位 + 显隐，上限作为配置常量 |
| 时钟源混淆（模拟钟 vs 墙钟） | 挂机时长计算错误 | 09 中明确分离：模拟钟仅战斗/测试驱动，墙钟仅挂机结算（framework 已有 `WallClock`） |
| 挂机 schema 演进 | 存档不兼容 | 复用 versioned-storage（ADR-013），字段变更走迁移 |

## 7. 里程碑验收标准

| 阶段 | 验收标准（可验证） |
|---|---|
| Stage 0 | `?smoke=auto-battle` 冒烟通过；截图确认敌左我右；血条/能量条视觉可区分；1x/2x/3x 切换生效且**同一对局三挡事件序列完全一致** |
| Stage 1 | 配置 `1v1`、`5v5`、`6v6` 均能正常对局与渲染；编队页点击填充/卸下/持久化恢复正确，开战单位与 lineup 一致；锁定目标：目标存活期间不换目标，死亡后顺延前排 |
| Stage 2 | 攻击有飘字（数值=事件 value）与闪白/抖动；入场/前冲/瞬移与事件对应；动画结束后单位姿态与 state 快照一致（无漂移） |
| Stage 3 | 离线 N 分钟返回获得收益（N 分钟×速率）；重启应用后收益与 lastSeenAt 保留；schema 版本迁移可验证；服务器迁移点（存储端口/收益纯函数/时间源）在文档与接口中明确 |

每个 change 的验收 = 上述阶段验收的子集 + openspec change 自身的 spec 场景全部通过。
